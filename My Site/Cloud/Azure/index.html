Azure Concepts
Concept Description
SKU (Stock Keeping Unit) - Describes a resource characteristics (type, class) (ex: VM SKU Standard_B1ls is a 1 CPU virtual machine, Standard_D2s_v4 is a 2 CPU virtual machine)
SLA (Service Level Agreement) - Describes the guaranteed uptime and performance of a service (ex: one standard VMs SLA is 99.5%% (3.6 downtime hours per month) )

Global Infrastructure

- Azure backbone -> Azure's global network

- Region -> Geographic location where one or multiple data centers reside

- A region might have only one data center (Azure doesn't work like AWS), at service deployment we can control where (or which availability zones) to deploy our servcies

- Regions can have pair regions (not always the case) for resiliency reasons, the pair region is located a the same geographic area at least 300 miles away

- Setting up the pair region is the developer's responsibility

- Availability Zone -> an individual data center group within a region

- Availability zones are for resiliency resons (redundant service availability), therefore availability zones exist at least in a group of 3 (numbered 1, 2, 3, ...)

- Availability zones have low latency connections between them

General Cloud Structure

- Azure Hierarchy -> There are 4 levels

- Management Group (High level management, controls quotas and policies, can be nested (6 depth max))

- Subscription (Used for billing, access control, and policies for its resources)

- Resource Group (Logical container for resources, used for organizing and managing resources)

- Resource -> the service itself

- Described as JSON template

- Must be part of one (but only one) resource group

- Resource groups can contain resources in different regions

- Not all resources are available in all regions (except global services)

- Scope -> a hierarchy level with all its sub levels (ex: subsription scope means all its resource groups and all those resource groups' resources)

- All resources within a scope are affected by the scope's roles and policies

- Tag -> additional information (key value pair)

- Can be assigned to a resource, resource group or a subscription

- Used for enhanced service management, automation, etc...

- Tags are not inherited in the hierarchy (by Default)

- Resource Lock -> prevent actions on the specified scope

- Can be assigned to subscription, resource group or resource scope

- At the time of writing this there are types of locks, CanNotDelete and ReadOnly

- Locks can be managed by administrators only

Access Control

- Access Methods (interaction Channels)

- Azure Portal -> GUI in the web browser

- PowerShell -> A module in PowerShell allow acces to Azure

- CLI -> Terminal access by using the az CLI

- Cloud Shell -> PowerShell or az CLI use through Azure Portal

- SDK -> Programmatic access to Azure

- Active Directory (Entra ID) -> Microsoft's cloud-based Identity and Access Management service (IAM) (Automatically created when creating Azure Account)

- Provides authentication and authorization for Microsoft and 3rd party services (uses protocols like OAuth 2.0, OpenID Connect, SAML, and WS-Federation)

- Tenant (also called directory) is an Active Directory instance, it represents a unique organization or entity, it's a namespace for users, groups, and applications, it's responsible for managing identities, authentication, and authorization for these objects)

- A tenant is bound to one or more Subscriptions (one-to-many relationship), (but a subscription can only be associated with one tenant)

- An Azure account can have multiple tenants

- There are different Entra ID plans (Free, P1, P2 and Entra Suite)

- Through a tenant we can manage important access policies like (self service password reset, authentication methods (SMS, email, authenticator app, etc...))

- Entra ID Connect -> hybrid authentication (between on-premises and Entra ID) (Password Hash Sync (PHS), Pass-through Authentication (PTA), Federation with AD FS)

- Microsoft 365 Admin Center -> web-based portal for managing access to Microsoft 365 services (Teams, SharePoint, Exchange, ect...)

- This is where administrators manage user access to Microsoft 365 services (ex: licences are managed here)

- Security Principal -> one identity in Azure that can be:

- User

- Group (can have owners who manage the group)

- Assigned -> user added/removed manually

- Dynamic -> user added/removed automatically based on defined rules (ex: all users with "Sales" in their job title)

- Service Principal -> technical user

- Application Registration -> the app registration in Active Directory

- Enterprise Applicaton -> basically a list of service principals

- Managed Identity -> authenticates resource without credential management

- A resource that allows applications and services to authenticate to Azure resources without needing to manage credential (eliminates credential management like, connection strings)

- 2 types:

- system assigned -> automatically assigned on resource creation, its lifecycle is tied to the resource (created and destroyed with the resource)

- user assigned -> independenly created from any other resources, the user is responsible for its management (can be attached to multiple resources)

- App Registration -> technical user













- Role -> in Azure we user RBAC (Role Based Access Control) in order to give priviledges to our users

- [Security Principal (User, Group, ...)] -> [Role] -> [Scope (Resource, Subscription, ...)] (Who -> What kind of rights -> To Which resource)

- RBAC is an authorization mechanism not an authentication one

- Policy -> Limitation of resources (ex: location restriction) (built-in or custom)

- Can be assigned to a resource group or any higher scope (cannot be assigned to a single resource directly)

- Applying a policy to a scope will affect current and future resources only (but we can "remediate" to apply newly assigned policies to already existing resources as well)

- We can define what action to take when the policy is violated (block, warn, etc...)

- Initiative -> A collection (group) of policies

Cost Management

- We should use the right services for our needs in order to save money (ex: a spot VM could be a cheap option for non essential computing)

- Cost Management -> resource where costs can be tracked and controlled

- Azure Calculator -> Azure tool to calculate service pricing

Azure DevOps

- Microsoft DevOps SaaS echosystem

- Boards -> Jira style ticketing system

- Repos -> Code repositories

- Pipelines -> CI/CD pipelines

- Concepts:

- Trigger -> Action that triggers the pipeline

- Template -> Pipeline script that can be imported and reused

- Agent -> Machine that execute the pipeline jobs

- Agent Pools -> A group of agents

- Artifact -> The output of the pipeline process

- Stage -> A set of jobs representing a functional proces (like test, build, deploy, etc...)

- Job -> A set of steps executed on the same Agent

- Step -> A Task or Script

- Task -> Azure built-in script (like UsePythonVersion@0 sets up a specified Python version)

- Script -> A set of commands executed in bash os PowerShell

- Artifacts -> hosts & shares software packages

- Test Plans -> provides manual testing environments and tools (we can use all sorts of VMs for manual testing)

Support Services

- Marketplace -> marketplace for services or service groups built by Microsoft or 3rd party vendors

- App Configuration -> configuration store for storing configuration data and feature flags

- Advizor -> Gives recommendations according to Azure best practices (Cost, Security, Reliability, Performance, Operational Excellence)

Security Services

- Security Center -> Continouously scans resources for security issues (gives feedback in Azure Advizor)

- functionalities can be enhanced by adding VMs

- Azure Sentinel -> Azure SIEM (Security Information Event Management) and SOAR (Security Orchestration Automation and Response) service

- Detect, investigate, and respond to security threats

- Key Vault -> Centralized secret storage store

- we can use SDK to access these secrets

- monitored service

Messaging Resources

- Event Hub -> high-throughput message broker that collects, transfomrs and stores large amounts of data

- can ingest millions of events per second

- retains data for days (1 to 7), so multiple services can read the same data from it

- supports multiple protocols (AMQP, HTTP, Kafka)

- each Event Hub contains several partitions, these are basically message channels where the order is garateed, however you need to specify a partition key in your message to make sure that they land to the same partition, otherwise messages are distributed in round-robin fashion across partitions

- the Event Grids Namespace is a logical container where several Event Grids live, it's basically provides, throughput config, access control and scallability for a group of Event Grids

Logging & Monitoring

- Azure Monitor -> Echosystem for various azure logging and monitoring services

- Log Analytics Workspace -> Azure Monitor's centralized log data storage for various Azure Monitor services (accessed by Kusto Query Language (KQL))

- Application Insights -> Resource that performance monitor and diagnosis other resource(es) (by default stores data on its own resource)

- Data Collection Rule (DCR) -> Resource that defines what logs & metrics should be collected about a host machine

- It's basicaly a blueprint for data collection (that's why it's a resource )

- defines: whant to collect (CPU, memory, sys logs, etc...), how to transform (filter) and where to send the collected data

Big Data Analytics tools (Ingest -> Transform -> Store -> Serve)
